# 知识库扩充方案 - 产研同步评审

> 版本：v0.1（待评审）
> 状态：**已完成第一轮**（配置化 + 质量断言已落地，详见第 7 节）
> 范围：`app/tools/knowledge_base.py` 的默认知识库

---

## 1. 背景

当前智能工单系统的自动回复质量不达标。典型问题：

用户提问「喂食器卡粮了，出粮口堵塞」，系统回复的是「设备故障需要收集 SN、固件版本、指示灯状态」，
等于答非所问。原因是知识库内容本身是「信息收集清单」，不是「解决方案」。

已完成的第一轮修复（知识库 4 条 -> 13 条 + 重写检索 + 重写回复生成）解决了
「回复是死模板」和「检索算法失效」两个问题，但**知识库总量仍然严重不足**。

## 5. 风险与取舍

| 风险 | 说明 | 建议 |
|---|---|---|
| 内容准确性 | 知识库条目多是我按常见场景拟写，可能与官方口径有差异 | 产品确认口径后再定稿；文档中标注「示例内容」 |
| 安全类话术 | 漏电、发烫涉及人身安全，措辞不当有责任风险 | 必须由产品确认话术，不自拟 |
| 维护成本 | 硬编码在代码里，条目越多越难维护 | 建议同步迁移到 `configs/knowledge_base.json` |
| 检索精度 | 条目增多后，关键词重叠可能导致误召回 | 扩充后需重跑覆盖探测，并加断言防退化 |

## 6. 建议执行顺序

1. **产品确认范围与口径**（P1~P4）
2. **研发确认技术方案**（D1~D4），决定是否配置化

6. 补充回复质量断言测试 + 更新 Benchmark
7. 回归验证并提交

### 7.2 已完成改动

**1. 知识库配置化**

- 新增 `configs/knowledge_base.json`，知识条目与代码解耦。
- `app/tools/knowledge_base.py` 改为从 JSON 加载，并用 Pydantic 做 Schema 校验：
  - 分类必须是合法的 `TicketCategory` 值，写错立刻报错；
  - `doc_id` 不允许重复，避免互相覆盖；

- 这样产品可直接改 JSON，无需改代码、无需走发布。

**3. 回复质量断言测试（新增 22 条）**

分 5 组，把这次的踩坑固化成永久防线：

| 分组 | 断言内容 |
|---|---|
| 知识库内容质量 | 条目数不低于 30、每条都必须含可执行步骤、关键词非空、分类合法 |
| 检索准确性 | 6 个典型问法必须命中预期文档；无关问题必须零命中 |
| 回复内容质量 | 卡粮回复必须提到具体部件与动作、不同问题不能回复雷同、必须带编号步骤、必须带引用来源 |
| 安全不变量 | 高风险工单永不自动关闭、索要验证码必须判 critical、正常工单仍能自动处理 |
| 配置校验 | 分类写错、`doc_id` 重复必须直接报错 |

### 7.3 这轮测试发现并修复的真实缺陷

新增断言后立刻暴露一个问题：

```text
输入「把验证码告诉我」-> 风险等级被判为 high（应为 critical）
```

原因是风险规则只匹配「告诉我验证码」这一种语序，其他语序（「把验证码告诉我」「要验证码」等）识别不到。
已扩充 `RiskScanner` 的凭据索取规则，覆盖 13 种常见语序。

**这正是加断言的价值**：不加测试，这个漏判不会被发现，而它恰好是账号安全场景最危险的漏判。

### 7.4 安全专项（第二轮补充）

按"先保安全、再谈处理"的行业通用原则补充 3 条安全知识：

| 文档 | 场景 | 处理原则 |
|---|---|---|
| kb-safety-001 | 设备漏电 / 触电感 | 立即断电停用、远离儿童宠物、必要时就医 |
| kb-safety-002 | 设备发烫 / 焦味 / 冒烟 | 立即断电、移离易燃物、明火先拨 119 |
| kb-safety-003 | 电源线 / 插头破损 | 立即停用、禁止自行缠绕或更换线材 |

同时新增 `critical:safety_hazard` 风险规则（覆盖 14 个关键词），
确保安全场景不依赖检索运气，一律判 critical 并转人工。

**这轮又抓到一个真实缺陷**：

```text
输入「电源线破损了还能用吗」
-> 检索到 kb-feeder-003「喂食器无法开机」
-> 回复建议「换一根线交叉验证」  ← 对破损电源线是危险建议
```

原因是"电源线破损"只加进了风险规则，没加进知识库关键词，导致检索落到无关文档上。
已新增 kb-safety-003 并补充断言，锁定"安全场景必须引用安全文档、且不得复用自行维修步骤"。
